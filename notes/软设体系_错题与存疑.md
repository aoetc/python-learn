## Ch1 · 软件工程与软件设计

### 1.1 过关记法（2026-09-20）

- **能跑** ≈ 做出了一个小项目。  
- **软件工程** ≈ 当成可维护、可加功能的工程来做。  
- 堆单文件最先痛：加功能/改代码难定位、协作易互相覆盖、维护成本高。

### 1.2 过关 + 易混（2026-09-20）

- 五段：需求 → 设计 → **实现** → 测试 → 维护。  
- **易混：** 「拆模块、数据怎么放」属**设计**；「写代码」属**实现**。（口述时把两词说清楚即可；你本意已对。）  
- 测试：故意试各种错，程序要能反应、尽量不崩。  
- 维护：改 bug、加功能。

### 1.4 易混 · 重复逻辑（2026-09-20）

- **误：** 两段逻辑一样、各自能跑、功能独立 → 对质量没伤害。  
- **正：** 当下能跑 ≠ 质量好。读文件路径/`encoding` 要改时，复制两份就要改两处，容易漏改 → **可维护性**差。  
- 功能独立（list 和 summary 职责不同）没问题；**相同的实现细节复制多份**才有问题。

### Ch1 资产定稿（2026-09-20 · 答辩可用）

1. **系统：** `dca-ledger` 定投账本（记一笔、列表、汇总/查找）。  
2. **不设计会痛：** 难以维护，修 bug 不好定位。  
3. **概要设计三块：**  
   - **命令入口**——选择用哪个功能；  
   - **读写账本**——和 CSV 打交道（写入 add，读出 list/统计也会读）；  
   - **统计**——汇总、查找等「算完再输出」。  
4. **质量句：** 这样分是为了可维护、好扩展。

## Ch3 · 软件设计基础（直觉预告）

### 高内聚 · 过关（2026-09-20）

- 一个函数/一块代码**围着一个主要功能**写 = 高内聚。  
- 不相关的事塞一起（如 `do_add` 里既校验金额又按月画图）= **内聚低**。

### 落地 · ledger_path（2026-09-20）

- 已在 `dca-ledger/main.py` 抽出 `ledger_path()`，`do_add` / `do_list` / `do_summary` / `do_find` 共用。  
- 答辩可说：为了**可维护**，路径只改一处。

## Ch2 · UML

### 用例图 · 过关（2026-10-09）

- 用例图答：**谁干什么**（参与者 + 用例）。  
- **不是用例：** 「打开 CSV」等实现细节；用例写用户目标。  
- **ledger 素材：** 参与者=用户；用例=记录流水、查流水、算总额（还可加「按日期查找」）。

### 类图 · 易混（2026-10-09）

- 类图答：系统里**有哪些块、怎么连**（不是「有什么功能」——那是用例图）。  
- 用户一般不进类图（系统外参与者）。  
- **易混：** `add`/`list`/`summary` 是用例/命令，不是类；类更贴近职责块（命令入口 / 账本存储 / 统计）。

### 类图 · ledger 素材定稿（2026-10-09）

1. **命令入口** — 选命令、分发。  
2. **账本存储** — 读写 CSV（不只增添，list/统计也会读）。  
3. **统计** — 按日期查找、算总额等。

### 顺序图 · 易混（2026-10-09）

- **误：** 顺序图 = 一个类里功能的先后。  
- **正：** 顺序图 = **一件事**里，多个对象**之间**谁先谁后发消息。  
- 「记一笔」可以没有统计；「算总额」一般要有统计（还要读账本）。

### 顺序图 · 过关（2026-10-09）

- 顺序图答：一件事里，**多个块之间**谁先谁后发消息。  
- **记一笔：** 1) 用户→命令入口：选 add 2) 命令入口→账本存储：追加一笔 3) 存储完成→入口→用户：已保存（统计可不出现）。  
- 「算总额」一般要有统计 + 读账本。
